# План разработки Anchorpass

Рабочий план нового монорепозитория с пакетами Python, npm для Node.js, Go и Rust. Цель — синхронный и асинхронный интерфейсы, выбор HTTP-транспортов по воспроизводимым измерениям, обязательная поддержка необязательного аргумента `proxy` и обновление совместимых данных протокола без переустановки пакета.

Решения пользователя: все перечисленные языки; настоящий блокирующий интерфейс Node; исходный `bg` из PyPasser; выбор распространённых HTTP-клиентов по скорости и устойчивости; переход с `invisible_captcha_bypasser` без обёртки совместимости. Остальные значения и интерфейсы ниже — предлагаемый контракт для реализации. Зависимости окончательно выбираются после проверки возможностей и бенчмарков.

На момент подготовки первоначального плана репозиторий был инициализирован на `main`, коммитов и реализации не было. Теперь локальные пакеты и проверки созданы; фактический статус и оставшиеся условия выпуска указаны в `docs/implementation-status.md`. Сам план не заменяет результаты проверок.

## 1. Объём и проверяемый результат

- Первоначальный протокол — HTTP-поток reCAPTCHA v3, рассмотренный в исходниках PyPasser; варианты `api2` и `enterprise` проверяются отдельно. Поддержку конкретного варианта объявляем только после проверки.
- Каждый пакет работает самостоятельно, без установки других языковых реализаций и без общего обязательного бинарного ядра.
- В каждом языке доступны блокирующее использование и неблокирующее сетевое выполнение. В Go одна функция с `context.Context` вызывается прямо или в горутине.
- Успешный библиотечный результат содержит полученный токен. Принятие токена и оценка сервером сайта — отдельный результат интеграционной проверки, который библиотека не выдумывает.
- Если передан `proxy`, он используется для всех сетевых шагов обращения к капче. Ошибка прокси никогда не приводит к автоматическому прямому соединению. Без аргумента допускается прямое подключение.
- Установленный пакет принимает новые данные совместимого протокола. Новая логика или несовместимый формат требуют выпуска кода.
- Получение данных при импорте, фоновые вечные потоки обновления, автоматическая ротация прокси и дополнительные виды капч в первоначальный объём не входят.

Первый обязательный результат — узкий рабочий прототип в контролируемом окружении с серверной проверкой принятия. До его получения допустимы контрактные тесты и технические прототипы, но масштабирование реализации на все языки остаётся предварительным.

## 3. API и владение ресурсами

Предлагаемые формы вызовов, не готовый код:

| Язык | Разовый вызов с прокси | Повторное использование |
|---|---|---|
| Python sync | `solve(anchor_url, proxy=proxy_url)` | `with Client(proxy=proxy_url) as client: ...` |
| Python async | `await asolve(anchor_url, proxy=proxy_url)` | `async with AsyncClient(proxy=proxy_url) as client: ...` |
| Node async | `await solve(anchorUrl, { proxy: proxyUrl })` | `new Client({ proxy: proxyUrl })` |
| Node sync | `solveSync(anchorUrl, { proxy: proxyUrl })` | `new SyncClient({ proxy: proxyUrl })` |
| Go | `Solve(ctx, anchorURL, WithProxy(proxyURL))` | `NewClient(WithProxy(proxyURL))` и `client.Solve(ctx, anchorURL)` |
| Rust async | `Client::builder().proxy(proxy_url).build()?.solve(anchor_url).await` | Тот же `Client` |
| Rust sync | `blocking::Client::builder().proxy(proxy_url).build()?.solve(anchor_url)` | Тот же blocking-клиент |

Дополнительно согласован контракт динамических параметров. Названия отражают действие:

| Язык | Загрузка актуального проверенного `bg` | Извлечение action без сети |
|---|---|---|
| Python | `load_bg`, `aload_bg`; метод клиента `load_bg` | `extract_action` |
| Node | `loadBg`, `loadBgSync` | `extractAction` |
| Go | `LoadBG` | `ExtractAction` |
| Rust | `load_bg` в async и blocking API | `extract_action` |

`solve` принимает необязательные `bg` и `action` средствами соответствующего языка. Переданные значения действуют только на текущую операцию и не меняют общий снимок или кэш. При отсутствии `bg` используется проверенный bundle. Приоритет action: явный аргумент → `sa` из anchor URL → отсутствие поля; универсальное значение для всех сайтов не задаётся. `action` передаётся как `sa` и в anchor, и в reload. `extract_action` ничего не угадывает и не выполняет JavaScript. `load_bg` соблюдает политику кэша/обновлений и не обещает обязательный сетевой запрос; принудительную проверку выполняет `refresh`. Точный контракт закреплён в `spec/api.md`.

Прокси фиксируется при создании клиента. Для смены маршрута создаётся другой клиент; это исключает неоднозначность уже открытых соединений. Разовые функции создают и закрывают принадлежащие им ресурсы. Пользователь, которому важно переиспользование соединений, использует клиент.

Имена `Result`/`SolveResult` адаптировать к языку. Смысл результата: `token`, `bundle_revision`, использованная версия протокола, длительность. Диагностика не содержит токенов, тела запроса или учётных данных прокси. Наличие результата не означает подтверждённую оценку сайта.

Клиент владеет своим HTTP-пулом. Cookies и изменяемые данные операции изолированы; повторное использование TCP/TLS-соединений не должно объединять cookie-хранилища разных операций. Не менять глобальные настройки HTTP-библиотеки. Контракт потокобезопасности фиксируется по языкам: async-клиент Python принадлежит своему циклу событий; синхронный клиент Python первоначально принадлежит вызывающему потоку; конкурентный доступ в Go/Rust и Node async проверяется отдельно. `SyncClient` Node обслуживает вызовы последовательно.

Для Node: `close()` прекращает приём работы и инициирует освобождение ресурсов; `closeAsync()` подтверждает завершение worker. Одноразовый вызов обязан иметь проверенное поведение освобождения ресурсов даже в программе без последующих `await`. Для Go/Rust — идиоматичное закрытие/владение с документированными пределами отмены.

## 4. Обязательный контракт прокси

Аргумент `proxy` принимает абсолютный URL с явными host и port. Query и fragment запрещены, path допускается только пустой или `/`. Пробелы, некорректные port и percent-encoding отклоняются без попытки автоматически исправить URL. Примеры формата с синтетическими значениями: `http://user:pass@127.0.0.1:8080`, `https://proxy.example:8443`, `socks5h://user:pass@127.0.0.1:1080`.

| Значение | Предлагаемое поведение |
|---|---|
| Не передано либо явно выбрано отсутствие прокси средствами языка | Прямое соединение |
| `http://host:port` | HTTP-прокси; HTTPS-цель через CONNECT |
| `https://host:port` | TLS до прокси и отдельная проверка TLS целевого сервера |
| `socks5h://host:port` | SOCKS5, разрешение имени целевого сервера на прокси |
| `socks5://host:port` | SOCKS5, локальное разрешение имени целевого сервера |
| Пустая строка, неизвестная схема, некорректный URL | `InvalidProxy` до любых сетевых запросов |

Это семантика Anchorpass. Нельзя просто передать схему исходной библиотеке и считать поведение одинаковым: например, [Requests различает local/remote DNS по схемам](https://requests.readthedocs.io/en/latest/user/advanced/#socks), а [Go net/http считает socks5 и socks5h эквивалентными](https://pkg.go.dev/net/http#Transport). Для локального DNS в таком случае нужен адаптер. До замеров каждый адаптер проходит проверку возможностей. Если обязательный режим нельзя реализовать и проверить с выбранным клиентом, кандидат исключается или получает явно обоснованный адаптер. Заявлять поддержку режима с другой семантикой запрещено.

Требования:

- Все запросы операции к капче, включая получение `v`, anchor и последующие шаги, идут через один нормализованный маршрут. Redirect не может изменить маршрут или выйти за разрешённые адреса.
- При ошибке подключения, авторизации, DNS или TLS нет повторного запроса напрямую. Неверный прокси не превращается в отсутствующий.
- `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY` и их варианты регистра не влияют на маршрут по умолчанию. Чтение окружения в первый контракт не включаем.
- Авторизация HTTP Basic для HTTP(S)-прокси и SOCKS5 username/password обязательна. Базовый переносимый набор credentials — ASCII; расширение до Unicode требует отдельной проверки. Спецсимволы в URL кодируются percent-encoding и декодируются ровно один раз, `+` остаётся плюсом; IPv6-адрес задаётся в скобках. NTLM/Kerberos не входят в первоначальный объём.
- Проверки сертификатов прокси и цели включены. Для закрытого центра сертификации предусмотреть отдельные настройки доверенных сертификатов; отключение TLS-проверки не использовать в бенчмарках как способ ускорения.
- `socks5h` запрещает локальное разрешение имени цели. Разрешение имени самого прокси может выполняться локально. При локальном DNS исходный hostname сохраняется для HTTP Host, SNI и проверки сертификата цели.
- Учётные данные передаются только соответствующему прокси. Их нет в обычных логах, диагностике, `repr`/`Debug` клиента, отчётах бенчмарков и сообщениях ошибок.
- Поддержку прокси при обращении к серверу сайта, который принимает полученный токен, библиотека не может обеспечить за приложение пользователя. В документации отдельно показать, как сохранить нужный маршрут в приложении.
- Неизменный URL прокси не гарантирует неизменный внешний IP у провайдера с ротацией. Для сценариев, которым нужна неизменная сессия, проверять соответствующую настройку провайдера; библиотека не обещает её обеспечить одним аргументом.

Загрузчик обновлений имеет отдельную HTTP-сессию без cookies и параметров решаемой капчи. У `updates_proxy` три разных состояния: аргумент отсутствует — `inherit` от `proxy`; явно передан `None`/`null` — `direct`; передан URL — отдельный маршрут. Python использует внутренний sentinel для отсутствующего аргумента, Go/Rust — явный тип режима. Строки `inherit` и `direct` в этом описании обозначают режимы, а не дополнительные форматы Proxy URL. Отказ наследованного прокси не переключает обновления напрямую. Это разделение маршрута и cookies сохраняется и внутри Node worker.

Приёмочные сценарии прокси: прямой режим; CONNECT; TLS до прокси; правильный/неправильный пароль; SOCKS5 с обеими политиками DNS; percent-encoded credentials; IPv6; недоступный прокси; попытка обхода через `NO_PROXY`; разрешённый/запрещённый redirect; одинаковый маршрут каждого шага; все режимы `updates_proxy`. Локальный управляемый прокси считает соединения, а тестовый origin фиксирует, откуда они пришли. Отрицательный контроль делает origin доступным напрямую при сломанном прокси: запрос должен завершиться ошибкой без обращения к origin. DNS-контроль использует имя, разрешимое только на стороне прокси: remote-режим проходит, local-режим возвращает ошибку. SOCKS fixture фиксирует домен или IP в запросе, origin проверяет Host/SNI и отсутствие proxy credentials.

## 5. Срок выполнения, отмена и ошибки

Общий срок `solve_timeout` отсчитывается монотонными часами с входа в `solve`. Он охватывает получение ресурсов, обязательную загрузку данных, разрешение имён, соединения, чтение ответов, повторные попытки и передачу результата из Node worker. Таймауты отдельных стадий ограничены оставшимся временем. Предварительный явный `prepare()` имеет собственный ограниченный срок.

Один параметр `timeout` сторонней библиотеки не считается доказательством соблюдения этого контракта. Проверять медленное поступление байтов, зависание DNS/прокси, CONNECT, TLS и чтение тела. Адаптер, который возвращает ошибку, оставляя бесконтрольно работающий поток, проверку отмены не проходит. Обычная библиотека не обещает точность реального времени при остановке процесса ОС; допуск планировщика явно учитывается в тестах.

Предлагаемые начальные ограничения для прототипа; окончательные значения фиксируются после измерений, до первого публичного выпуска. Все значения задаются конфигурацией клиента, не подбираются по мощности машины разработчика.

| Параметр | Начальное значение |
|---|---:|
| `solve_timeout_seconds` | 30 |
| `connect_timeout_seconds` | 5 |
| `read_idle_timeout_seconds` | 5 |
| `update_timeout_seconds` | 5 |
| `max_in_flight` для конкурентного клиента | 16 |
| `max_queue` | 0, немедленный `ResourceLimit` при перегрузке |
| `max_response_bytes`, включая распакованный ответ | 1048576 |
| `max_bundle_bytes`, включая распакованные данные | 65536 |
| `max_sync_result_bytes` | 65536 |
| `get_max_attempts`, включая исходный запрос | 2 |
| `reload_max_attempts` | 1 |
| `worker_limit_per_isolate`, включая завершающиеся workers | 4 |
| Одновременных sync-вызовов на Node-клиент | 1 |
| `refresh_interval_seconds` | 3600 |

Лимиты соединений согласованы с `max_in_flight`; внутренних неограниченных очередей нет. Лимит тела проверяется потоково, до накопления полного ответа. Для ошибок и вывода worker также нужны ограниченные буферы.

Повторы разрешены только для явно перечисленных безопасных GET-шагов и временных сетевых ошибок, в общем сроке операции. Неверный прокси, ошибка авторизации, сертификата, подписи, формата или входных данных не повторяются. POST-шаг с неопределённым результатом отправки автоматически не повторяется. Ответы ограничения частоты не обходятся сменой маршрута; повтор, если допустим, учитывает `Retry-After` и оставшийся срок. Скрытые повторы транспорта отключить или включить в общий счётчик.

Общие категории ошибок: `InvalidInput`, `InvalidProxy`, `UnsupportedProxy`, `ProxyConnectError`, `ProxyAuthError`, `TransportError`, `DeadlineExceeded`, `Cancelled`, `HttpStatusError`, `ProtocolError`, `ConfigUnavailable`, `ConfigInvalid`, `ConfigExpired`, `ConfigRollback`, `ResourceLimit`, `WorkerUnavailable`, `ClientClosed`. Публичные типы идиоматичны каждому языку; стабильны категория, стадия и признак возможности повтора. Конкретную ошибку прокси выдавать только при наличии данных для её различения; иначе использовать обобщённую сетевую ошибку.

## 6. Обновляемые данные

Независимо версионируются код пакета, контракт протокола и ревизия данных. Загрузчик не скачивает исполняемые скрипты, регулярные выражения или произвольные шаблоны запросов. Поля bundle входят в закрытый список, проверяются по типу/длине и кодируются штатным form encoder языка.

Предлагаемый формат: envelope с base64 точных UTF-8-байтов payload, `key_id` и подписью Ed25519. Подписываемое сообщение задаётся точным тестовым вектором с меткой Anchorpass, версией формата, идентификатором ключа и однозначным разделением полей. Подпись проверяется до использования payload; JSON не пересериализуется для проверки. Алгоритм фиксирован кодом.

Payload включает `schema_version`, `protocol_family`, `revision`, `issued_at`, `expires_at`, список поддерживаемых возможностей и разрешённые данные протокола. Ревизия — ограниченная строка десятичных цифр без ведущих нулей, со сравнением по длине и затем лексикографически; это исключает зависимость от числовой точности языка. Дубликаты JSON-ключей, некорректный UTF-8 и неоднозначные значения отклоняются.

Совместимость задаётся общим идентификатором контракта и возможностями, которые код умеет обрабатывать. Версия Python-пакета сама по себе не определяет совместимость Rust-пакета. Для разных семейств/несовместимых поколений — отдельные каналы и сохранённые пороги ревизий.

Доверенные открытые ключи входят в пакет. План ротации ключей и способ доставки нового доверия фиксируются до выпуска; неизвестный ключ не принимается из самого bundle. При потере доверия к единственному ключу может понадобиться обновление кода. Время жизни подписанных данных и период поддержки старого канала утверждаются до публикации; автоматическое бесконечное продление без проверки данных запрещено.

### Выбор данных

`refresh_interval` определяет, когда проверять наличие новой ревизии. `expires_at` определяет, разрешено ли использовать данные. Сетевая ошибка не продлевает `expires_at`.

| Состояние | Автоматический режим | `offline` | `pin(revision)` |
|---|---|---|---|
| Совместимый подписанный локальный bundle допустим, проверка ещё не нужна | Использовать без сети | Использовать | Использовать, если ревизия совпадает |
| Bundle допустим, пора обновляться | Ограниченная проверка; при сетевом сбое использовать текущий | Использовать без сети | Проверку новой ревизии не выполнять |
| Локальных допустимых данных нет | Попытаться получить совместимый bundle в пределах срока | `ConfigUnavailable` | Получить только указанную ревизию, если сеть разрешена; иначе ошибка |
| Истёк срок данных | Искать допустимые новые данные; при неудаче ошибка | `ConfigExpired` | `ConfigExpired` |
| Неверная подпись/формат кандидата | Отклонить кандидат; допустимый текущий снимок можно сохранить | Отклонить | Отклонить |
| Ревизия кандидата ниже ранее принятой | Отклонить кандидат | Отклонить | `ConfigRollback` |
| Та же ревизия, другие байты payload | `ConfigInvalid` для кандидата | То же | То же |
| Новый bundle несовместим | Не повышать порог; сохранить допустимый совместимый снимок | Не использовать | Не использовать |

`pin` запрещает незаметное переключение на другую ревизию; он не отключает подпись, срок действия или защиту от отката. `offline` управляет только загрузчиком данных: запросы к капче по-прежнему требуют сети. Для работы без сервера обновлений приложение может заранее предоставить подписанный совместимый bundle. Автоматического льготного периода после expiry в первом контракте нет. Это осознанное ограничение доступности, которое требуется явно описать пользователям до выпуска.

Обновление между операциями меняет только снимок для последующих операций. Начатый `solve` использует одну ревизию и один `v`; срок bundle должен покрывать разрешённый срок этой операции, иначе сначала нужен refresh либо ошибка. Фоновое обновление не заменяет поля уже начатого запроса.

### Кэш и публикация

- Один refresh в процессе на сочетание канала и сетевой политики; ожидающие клиенты сохраняют собственные сроки отмены. Отмена одного ожидающего не должна необоснованно отменять обновление для остальных.
- Клиентский снимок в памяти. Дисковый кэш хранит точные подписанные байты, принятый порог и идентификатор payload; запись состояния атомарная с ограниченным ожиданием блокировки.
- При read-only файловой системе допустим проверяемый режим памяти. Он не обещает защиту от отката между перезапусками. Удаление всего состояния также снимает локально накопленный порог; это не маскируется под сохранённую гарантию.
- Если дисковая запись не удалась, обновление можно принять только как явный режим памяти с диагностическим статусом; не объявлять состояние сохранённым. Просроченный/невалидный текущий bundle использовать нельзя.
- HTTPS-источник фиксирован, redirect запрещён по умолчанию. Канал хранит неизменяемые объекты по ревизии и небольшой подписанный указатель на актуальную ревизию для поддерживаемого контракта. Указатель связывает ревизию и digest; cache TTL не может продлить подписанную допустимость.
- Новые данные проходят общие проверки и контролируемую интеграционную проверку, подписываются и публикуются отдельным процессом от пакетов. Приватные ключи подписи не включаются в репозиторий или клиент.
- Откат ошибочных значений — новый подписанный выпуск с большей ревизией и прежними проверенными значениями. Старые номера не перезаписываются.
- Нужны тесты повреждения кэша, конкурирующих процессов, обрыва записи, истёкших данных, отклонения часов, смены ключа и чтения новым пакетом старого состояния. Строгую свежесть без корректных часов и сохранённого состояния не обещаем.

## 7. Node sync

Основной кандидат для долгоживущего `SyncClient` — постоянный worker. Он владеет async-ядром и HTTP-пулом, получает только сериализуемые проверенные параметры. Сравнение с отдельным процессом нужно для проверки издержек и разового сценария; новый процесс на каждый вызов не удовлетворяет требованию сохранения пула между вызовами.

Обмен: отдельный `SharedArrayBuffer` на вызов, идентификатор операции, ограниченный результат и атомарное конечное состояние. Worker сначала записывает результат, затем публикует готовность. Отмена не может быть перезаписана поздним успешным ответом.

Основной поток ожидает состояние по монотонному сроку. Он не ждёт Promise, таймер, обработчик `message`, `error` или `exit` в заблокированном цикле событий. Результат и ошибки не передаются через stdout. Авария worker до публикации может проявиться как истечение срока; без подтверждения нельзя объявлять её точно установленной причиной.

После срока ожидания клиент становится непригодным для новых вызовов, запрашивает отмену и завершение worker. Число живых, запускаемых и завершающихся workers ограничено; автоматической бесконечной замены нет. Область лимита — JavaScript isolate, а не весь процесс с несколькими isolates. Закрытый клиент не принимает новые запросы.

Прототип обязан проверить: handshake запуска, ошибку до готовности, сбой во время запроса, зависание, слишком большой ответ, гонку таймаута и результата, серию sync-вызовов без возврата управления циклу событий, закрытие, повторное закрытие, выход короткого CLI, отсутствие накопления workers и переиспользование соединения. Тестовый HTTP-сервер находится в отдельном процессе. Проверять упакованный helper в поддерживаемых форматах загрузки Node.

Если worker не проходит жизненный цикл, это блокирует выбор реализации sync API. Альтернативу с иными гарантиями ресурсов или производительности нужно сначала сопоставить с контрактом, затем согласовать существенное изменение; требование sync не удаляется.

## 8. Выбор транспортов и бенчмарки

Начальные кандидаты, без утверждений о победителях:

| Язык и режим | Кандидаты |
|---|---|
| Python sync | `requests`, `httpx`, `curl_cffi` как исходная точка |
| Python async | `aiohttp`, `httpx`, `curl_cffi` |
| Node | Встроенный `fetch`, `undici.request`, `axios` |
| Go | `net/http`; `resty` для оценки обёртки |
| Rust | `reqwest`, `isahc`; `ureq` для blocking |

Сначала проверка возможностей: весь контракт прокси и DNS, TLS, изоляция cookies, ограничение распакованного тела, управляемые повторы, общий срок и освобождение ресурсов. Возможность может требовать адаптера или отдельной зависимости; фиксировать её состав и размер в отчёте. Пакет получает выбранный транспорт для каждого режима, остальные остаются зависимостями стенда. Общий транспорт sync/async предпочтителен при сопоставимых результатах, но не обязателен.

Профили: разовый вызов; повторное использование клиента; параллельная работа; короткие и медленные ответы; HTTP/TLS-прокси; SOCKS; недоступный/медленный прокси; ограничение частоты; обрывы; медленное поступление тела; повреждённые и слишком большие данные. Для прототипа уровни параллельности `1`, `8`, `32`; при повышении явно увеличить проверяемые клиентские лимиты. Нагрузку не смешивать с проверкой отказа при превышении стандартного лимита.

Методика:

1. Зафиксировать ОС, архитектуру процессора, версии runtime и зависимостей, TLS backend, лимиты CPU/памяти/дескрипторов и конфигурацию сервера.
2. Выполнить прогрев; отдельно сохранить cold-start. Чередовать кандидатов и повторять измерения, сохранять исходные данные. Окончательный объём выборки определить пилотом, а не подбирать после получения удобного победителя.
3. Выравнять payload, число соединений, concurrency, redirects, retries, проверку TLS и семантику DNS. Сервер должен иметь запас мощности; насыщение сервера не выдавать за предел клиента.
4. Собирать p50/p95/p99, успешные операции в единицу времени, ошибки по категориям, CPU, пиковую память, число потоков/дескрипторов/соединений и время завершения после отмены.
5. Отдельно измерить загрузчик обновлений, чистый HTTP и полный API, включая Node bridge. Для cold и warm сравнения явно указывать наличие уже открытого соединения.
6. Проверить отсутствие роста ресурсов при повторных ошибках и перегрузке. Статистику, разницы и проценты вычисляет скрипт; сырые данные и команды сохраняются вне публикуемых пакетов.
7. Отбирать прошедших корректность и устойчивость. Затем сравнивать измеренные профили; при статистически неразличимом результате выбирать меньше зависимостей и проще сопровождение. Если профили дают разных победителей, не скрывать компромисс одним общим баллом.

Проверку принятия результата проводить отдельно, с ограниченной согласованной нагрузкой в контролируемом окружении. Локальный рейтинг HTTP-клиентов не доказывает равную совместимость с внешним сервисом. Данные из README upstream не являются нашими измерениями.

## 9. Общая проверка и сборки

Общие vectors покрывают входы, URL-кодирование и повторяющиеся параметры, специальные символы, пустые/неверные ответы, допустимые адреса, запросы/ответы по шагам, ошибки, retries, отмену, конфигурацию, bundle и прокси. Успешные примеры дополняются отрицательными контролями. Исполняемые тесты проверяют серверную последовательность и факт отсутствия лишнего обращения.

До выбора зависимостей составить `docs/compatibility.md`: поддерживаемые версии Python и Node, версия Go, минимальная версия компилятора Rust, ОС, CPU-архитектуры, форматы ESM/CommonJS и режимы прокси. Матрица не должна автоматически расширяться до всех платформ, где компилируется библиотека. Минимальные и актуальные поддерживаемые версии runtime проверяются в CI.

Команды реализованного каркаса; точные аргументы закреплены в Makefile и конфигурации CI:

| Область | Команды/проверки |
|---|---|
| Общий контракт | `make check-spec`, `make check-package-data`, `make test-conformance` |
| Python | `ruff check`, `ruff format --check`, `mypy`, `pytest`, `python -m build` |
| Node | `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`, `npm pack` |
| Go | Проверка `gofmt`, `go vet ./...`, `go test -race ./...`, `go build ./...` |
| Rust | `cargo fmt --check`, `cargo clippy`, `cargo test`, `cargo package` с матрицей async/blocking features |
| Интеграция | `make test-proxy`, `make test-updates`, `make test-package-install` |
| Измерения | `make bench-smoke`, затем явно выбранные профили полного стенда |

Точные команды с путями, flags и feature-комбинациями закрепляются в manifests, Makefile и CI при создании каркаса. При повторном запуске используем эти команды, а не отдельные несогласованные наборы.

С первой реализации включить CI. Изменение `spec/`, встроенных данных или генератора запускает проверки всех языков. Языковая правка запускает собственные проверки и затронутые общие сценарии. Live-проверки не являются обычными сетевыми unit-тестами; перед выпуском нужна отдельная актуальная запись интеграционного результата.

Артефакты проверять в чистой среде вне монорепозитория: Python wheel и sdist, npm tarball, Go module archive, Rust crate. Внутри должны находиться встроенный bundle, доверенные ключи, уведомления лицензии и Node helper. Установка/import без сети не должны запускать обновление. Проверить разовый вызов, повторное использование и поддержку прокси именно из упакованного артефакта.

## 10. Этапы работы и условия перехода

Локальный кандидат `0.1.0` реализован для всех языков. Выбор транспортов завершён; Rust получил отдельный Hyper/rustls-адаптер для независимого доверия цели и HTTPS-прокси. Выполнены общий [сравнительный стенд](benchmarks/reports/matrix/REPORT.md), отдельные [профили загрузчика и нагрузки](docs/pressure-results.md), проверка минимальных runtime, установка точных артефактов вне checkout и [принятие api2 демосервером через все публичные API](docs/live-acceptance.json). Enterprise проверен локально и не объявляется live-совместимым. Подготовлены манифест с SHA256, возобновляемая доставка, защищённый ручной workflow публикации и инструменты подготовки канала; инструкции — в [release operations](docs/release.md). Неподтверждённые production-параметры перечислены в [support policy](docs/support-policy.md). Этап внешнего выпуска остаётся отдельным: нет production-ключа/канала, доступа к реестрам и подтверждённого удалённого CI; публикация и изменение старого проекта не выполнялись. Текущие результаты проверок и ограничения находятся в [implementation status](docs/implementation-status.md).

### Этап 0. Подтверждение базового поведения

Создать минимальный Python-прототип по зафиксированной ревизии upstream. Проверить один полный сценарий напрямую и через тестовый прокси, включая подтверждение принятия на сервере контролируемого сайта. Подготовить обезличенные ответы для локальных тестов, сохранить версии и команды проверки. Варианты протокола учитывать раздельно.

Готово: повторяемый подтверждённый результат и отрицательный сценарий отказа; весь сетевой путь через proxy проверен. Если нет управляемого сайта/доступа к его серверной проверке, это именованная недостающая предпосылка. Контрактные работы могут продолжаться, но работоспособность метода и готовность выпуска не объявляются.

### Этап 1. Контракт, каркас и ранний CI

Зафиксировать доверенные ключи тестового стенда отдельно от будущих ключей выпуска. Согласовать срок допустимости данных и поддержку старых каналов до включения автоматической публикации.

Готово: схемы и vectors валидны; тестовый runner читает их; синтетический сервер/прокси запускается с ограниченным временем; команды CI доступны. Общие контракты прошли независимое ревью.

### Этап 2. Проверка транспортов и Node sync

Создать адаптеры стенда, capability tests и Node-прототип. Выполнить пилот, выбрать размер и длительность измерений, провести сравнительные профили. Исключить клиентов с неподходящими proxy/DNS/deadline/lifecycle. Зафиксировать версии победителей и необходимые дополнительные зависимости.

### Этап 3. Python и обновляемые данные

Реализовать чистое ядро, оба клиента, ошибки, прокси и ограничения. Создать producer bundle, подпись, loader, атомарный кэш, режимы pin/offline и ручной refresh. Подключить общие сценарии и установить собранный пакет в чистую среду.

Готово: sync/async проходят общие тесты, сетевую изоляцию и закрытие; установленный пакет получает новый совместимый bundle без изменения своего кода; несовместимый или испорченный bundle отклоняется; начатая операция сохраняет старый снимок. Минимальный Node-прототип проверяет тот же формат подписанных данных до его окончательного закрепления.

### Этап 4. TypeScript, Go и Rust

Реализовать пакеты независимо на зафиксированном контракте. Node включает проверенный sync bridge. Для каждого языка закрыть прокси, отмену, упаковку и собственные ограничения runtime. Ошибка эталонной реализации исправляется в контракте/тестах при наличии доказательства, а не копируется в остальные пакеты.

Готово: одинаковые vectors и последовательности выполняются во всех пакетах; доступны все обязательные режимы proxy; артефакты устанавливаются и тестируются отдельно; публичная документация отражает особенности каждого языка.

### Этап 5. Совместимость, отказоустойчивость и кандидат выпуска

Проверить матрицу «старый установленный пакет + новый совместимый bundle», несовместимый bundle, недоступный update server, expired cache, смену ключа, откат данных новой ревизией, конкурирующие процессы, read-only cache и повторные таймауты. Повторить только затронутые профили бенчмарков после изменений. Провести независимое ревью реальных реализаций и trust boundaries.

Готово: все обязательные проверки и установка артефактов проходят; нет незакрытых дефектов внутри объёма; ограничения documented; интеграционная проверка актуальна для выпускаемых версий. Данные и код можно выпустить раздельно, а предыдущие валидные артефакты доступны для воспроизводимости.

### Этап 6. Выпуск и миграция

Подготовить GitHub-репозиторий/remote, имена реестров, права публикации и подписывающую среду; доступность имён перепроверить перед публикацией. Первый согласованный выпуск пакетов использует общий номер версии. Позднейшие локальные исправления языка могут выпускаться независимо при неизменном контракте, с записью в матрице совместимости.

Теги: `py-vX.Y.Z`, `npm-vX.Y.Z`, `go/vX.Y.Z`, `rust-vX.Y.Z`; данные — отдельный тег с поколением протокола и ревизией. Публикация в разные реестры не атомарна: вести журнал фактически опубликованных артефактов и возобновлять только недоставленные. Не переиздавать существующую версию с другими байтами.

После установки и проверки публичного Anchorpass обновить README старого проекта: deprecated, прекращение сопровождения, ссылка на новый проект и `docs/migration.md`. Показать замену `solve_captcha`, аргумент proxy и новые ошибки. Старые версии не удалять, совместимую обёртку не добавлять. Публикация и внешние изменения выполняются отдельным явно разрешённым этапом; этот план их не выполняет.

Готово: пакеты доступны и проверены после установки из реестров; примеры миграции работают; канал данных обслуживает объявленные версии; порядок исправления неудачного выпуска документирован.

## 11. Разделение работы

Ведущий отвечает за общий контракт, решения, интеграцию и финальные проверки. После стабилизации контракта Python, Node, Go и Rust можно вести независимыми исполнителями с исключительным владением своими каталогами. Общие `spec/`, producer bundle и генератор имеют одного владельца; изменения согласуются до обновления потребителей. Стенд и сценарии отказов можно вести отдельной линией с собственными файлами. Независимый reviewer не переписывает решение.

Последовательная критическая цепочка: подтверждение поведения → контракт → возможности и измерения → реализация → совместимость и упаковка → выпуск. Работу, которая не зависит от результата live-проверки, можно выполнять параллельно, сохраняя её статус предварительной.

## 12. Решения, которые должны быть закрыты по ходу работы

| Решение | Как принимается | До какого этапа |
|---|---|---|
| Контролируемое окружение и критерий принятия результата | Проверка доступа к сайту и серверной верификации | Завершение этапа 0 |
| Поддерживаемые ОС, runtime и режимы импорта | Метаданные кандидатов и возможности CI; существенные сокращения объёма согласовать | Завершение этапа 1 |
| Буквальные значения expiry, clock-skew, границы JSON и политика ключей | Таблица отказов и требования доступности; существенный компромисс согласовать | До закрепления loader и первого выпуска данных |
| HTTP-клиенты и SOCKS/HTTPS адаптеры | Capability tests и бенчмарки | Завершение этапа 2 |
| Окончательные resource defaults | Измерения на ограниченной среде | До кандидата выпуска |
| Адрес канала данных и издательские доступы | Подготовленная проверяемая конфигурация размещения | До внешней публикации |
| Срок поддержки старых поколений протокола | Явная политика сопровождения | До первого публичного выпуска |

Ни один незакрытый пункт не считается уже реализованной гарантией. Обновлениями данных нельзя обещать бессрочную совместимость со всеми будущими изменениями сервиса.

## 13. Основания для технических ограничений

- [PyPasser в зафиксированной ревизии](https://github.com/xHossein/PyPasser/tree/910c3def3d69e68d42d86ccba5a1b4cf105ee1ed): исходное поведение и данные; перенос не заменяет нашу проверку работоспособности.
- [Requests timeouts](https://requests.readthedocs.io/en/latest/user/quickstart/#timeouts): параметр timeout не задаёт общий предел времени загрузки ответа.
- [Node worker threads](https://nodejs.org/api/worker_threads.html): завершение worker и ограничения блокирующего родительского цикла событий.
- [Node fetch](https://nodejs.org/api/globals.html#fetch): встроенный fetch основан на Undici; сравнение учитывает версии и интерфейсы.
- [Go module versions](https://go.dev/ref/mod#vcs-version): модулю в подкаталоге нужен соответствующий префикс тега.
- [Reqwest blocking](https://docs.rs/reqwest/latest/reqwest/blocking/): ограничения использования blocking API внутри async-runtime.

Перед выбором транспорта зафиксировать версии и перепроверить именно их возможности; наличие документации последней версии не гарантирует то же поведение минимальной поддерживаемой версии.
